# Recovery work package

This package installs no backup jobs and makes no recovery claim. Provider/region/cost, credentials, live operator compatibility, capture consistency and independent monitoring location remain inputs. Use the Paperclip project's `backup-restore-spec.md` as the authoritative requirements.

1. Inventory all three CNPG clusters, MariaDB/Galera, Redis, Portainer and other valuable PVCs, including the unclassified Planka volume. Determine actual owners, sizes/change rates and whether Redis is reconstructible. Do not copy live database directories as file backups.
2. Choose compatible object storage within an explicit cost estimate; validate current CNPG/Postgres/Barman plugin versions. Give each CNPG cluster a separate prefix/identity. Prepare reviewed Flux operator/plugin/ObjectStore/ScheduledBackup changes after this input is known. Prove daily base backups and the WAL chain support the proposed 30-day window and measure WAL freshness. Restore the shared cluster into isolated temporary resources and extract only `paperclip_eval`/future Paperclip database for scoped restoration; never revert unrelated applications.
3. Verify native MariaDB backups/log recovery and required Redis exports against installed versions. Record coverage per workload rather than calling partial backup rollout operational.
4. Authenticate rclone to existing Google Drive using a dedicated tested OAuth app/scope. Initialize an encrypted restic repository with its password retained independently. Confirm capacity, refresh, transfer duration, deletion/retention limits and fresh-machine recovery. Keep all backup/Drive/delete credentials outside runners and the controller. Do not create a CronJob that copies changing PVCs without a verified capture/quiescence mechanism.
5. Capture controller `/paperclip` and each runner `/home/node`, plus every effective managed runtime/session/auth path discovered in evaluation and required secrets/configuration. Include uncommitted files and unpushed commits. Coordinate database/file recovery boundaries, using an application-aware quiescence or verified snapshot mechanism. Plan 15-minute file captures with transfer margin; proposed retention is 48 hours frequent, 30 daily and 12 monthly, subject to measured cost/capacity.
6. Retain an encrypted recovery bundle for non-Git cluster configuration, application secrets, encryption keys, bootstrap credentials and image digests. Keep the decryption key independently accessible. Record replacement compute, MicroK8s bootstrap, network/storage/operator ordering and Flux suspension during restore.
7. Wire Telegram failure/recovery alerts and an **outside-cluster** heartbeat/freshness monitor. No Telegram messages are sent by this preparation. Warn at 30 minutes and hold new Paperclip work at 60 minutes. The actual admission/checkpoint control must be implemented against verified Paperclip dispatch paths and tested; disabling the timer scheduler alone does not block manual or demand-triggered runs. Do not claim a diagnostic freshness check is admission enforcement.
8. Rehearse isolated restore with outbound automation blocked, fresh volumes and a separate database. Validate login/history/attachments/decryption, provider login recovery and uncommitted work. Measure the oldest complete compatible recovery boundary (not upload completion time), loss within one hour and restore within four hours from operator response. Include cluster-storage loss/rebuild dependencies. Keep every unprotected workload and failed drill visible.

Activation of valuable Paperclip tasks remains blocked until these requirements have actual evidence. Restoration namespaces and storage must never overwrite production databases or PVCs. Provider token rotation may require controlled re-login; reconcile external pushes/PRs before reenabling work.
